# The ngit dataset - metric semantics reference

What every number on `/git` (Git-on-Nostr, NIP-34 (git collaboration)) counts, what it
excludes, and what it must not be read as. This is the AUTHORITATIVE rule text: the
production compute (`dagster_code/pipeline/ngit.py`) implements it, and the
independent cross-check (`crosscheck/ngit_check.py`) is written from it without reading that
code. A rule that is ambiguous here is a bug here. The surface design (pipeline, page,
operations) is `docs/design/ngit-design.md`, with the decisions behind the identity and
activity model. Written 2026-09-25; revised in place.

Notation: `tag[i]` is 0-based inside a tag array; "value" means `tag[1]`; "values" of a
tag means `tag[1:]`. Timestamps are UTC. Kinds are named `kind-NNNNN (slug)`.

## 1. Inputs and common preprocessing

Input rows per kind are the archive's events (`id`, `pubkey`, `created_at`, `content`,
`tags`, plus `d_tag` for the addressable kinds). Preprocessing, applied to every kind in
this order:

1. **id-dedup**: one row per `id`; when the archive holds an id more than once, the copy
   with the earliest `ingested_at` is kept (the extracts do this).
2. **Horizon**: the surface is "as of the last complete UTC day". `as_of_day` is the UTC
   date of `now_ts - 86400`; `as_of_end` is `as_of_day` 23:59:59 UTC. A row whose
   `created_at` is greater than `as_of_end` is dropped everywhere (a row created on the
   run's own partial day waits for the next run); among the dropped rows, those with
   `created_at` greater than the run instant `now_ts` are counted in
   `anomalies.future_dated` for their kind. A row whose `created_at` is before
   2023-01-01T00:00:00Z is dropped and counted in `anomalies.past_dated` (NIP-34 (git
   collaboration) did not exist; such a timestamp is a broken clock or an attack on the
   time axis). The kinds with anomaly slots: announcements, states, grasp_lists, comments,
   reactions, external_reactions, zaps; for comments, reactions, external reactions and zaps
   both slots count the admitted subset of section 6, as `summary.archive_events` does, so an
   out-of-scope row is counted nowhere. Deletion triples are filtered the same way but have
   no slot. `external_reactions` is first written by the first run after the nostrology-data
   deploy of 2026-10-11, in both anomaly blocks and in `summary.archive_events`; documents
   generated before 2026-10-12 may lack it, and every document generated from 2026-10-12 on
   carries it.
   `summary.archive_events` counts the rows that survive steps 1 and 2 per kind (for
   comments, reactions, external reactions and zaps: the admitted subset, section 6; for deletions: the
   distinct self-authored (author, coord) pairs with at least one surviving triple - a
   coord without a second colon names no repository and can match no announcement, but
   the pair still counts).
3. **Coordinate**: for kind-30617 (repo-announcements) and kind-30618 (repo-states),
   `(pubkey, d)` with `d` = the value of the first `d` tag, or `""` when there is none or
   the first `d` tag has no value. For
   kind-10317 (grasp-server-lists) the coordinate is `pubkey`.
4. **Version order** within a coordinate: `created_at` ascending, then `id` DESCENDING. The
   last row in that order is the **current version** (NIP-01 (protocol basics): among
   equal `created_at` the lowest id survives). "Previous version" means the row before in
   that order.
5. **Windows**: an "N d" window is the N complete UTC days ending on `as_of_day`,
   inclusive, judged on the UTC date of `created_at`. "7 d", "30 d", "90 d" follow. A "month" is the UTC
   calendar month of `created_at`; a "week" is the ISO week (Monday start) of `created_at`,
   labelled by its Monday's date.

Constants: `ANN_WALL = 2026-05-02T16:50:26Z`, `STATE_WALL = 2026-06-14T03:22:39Z`,
`COMMENT_WALL = 2026-06-18T02:59:29Z` (the earliest `ingested_at` of each kind in the dev
archive, which was seeded from an earlier deployment: they are the acquisition lineage's
dates).

## 2. Repository identity

### 2.1 Announcement (coordinate)

One kind-30617 (repo-announcements) coordinate. Its **first seen** is the `created_at` of
its earliest archived version; its **last seen** is the current version's `created_at`.
Attribute reads are on the current version unless a rule says otherwise:

- `name`: value of the first `name` tag, else `""`. `description`: likewise.
- `clone` values: the values of ALL `clone` tags (some clients spread values over several
  tags), trimmed (leading and trailing whitespace of any kind removed), empty strings
  dropped, in order, duplicates removed.
- `web` values, `relays` values: likewise.
- `t` values: lowercased and trimmed values of all `t` tags.
- `client`: value of the first `client` tag, else none. `alt`: likewise.
- `euc`: the value of the first `r` tag that has a third element equal to `euc` AND whose
  value is 40 lowercase hex characters (an `r` tag that meets only one condition is
  skipped, not chosen); if there is none, the value of the first `r` tag that has exactly
  two elements and whose value is 40 lowercase hex characters (the ngit v1.0-1.2 form);
  else none.
- **maintainer listing** (the pubkeys this announcement names): if any tag named `M`, `m`
  or `o` exists, the values of the ACTIVE `M` and `m` tags, where a tag is active when it
  has fewer than four elements or an odd number of elements; otherwise the values of all
  `maintainers` tags (every value of every such tag, `tag[1:]`, untrimmed). Each value is
  normalized: a 64-hex string (either case) lowercased, an `npub1...` string
  bech32-decoded to 64-hex when its checksum verifies and it decodes to 32 bytes; anything
  else is dropped. The announcement's own pubkey is removed from its listing.
- **self-lead**: true when an active `M` tag's value normalizes to the announcement's own
  pubkey.

### 2.2 Noise ledger

Applied to every announcement coordinate, in this order; the first matching rule is the
coordinate's `family`; a coordinate matching none is `repo` (kept). Rules read the current
version except N5, which reads the version history, and N6's deletion clause and N8b/N9's
state clause, which read other kinds.

| family | rule |
|---|---|
| N0 | `d` is longer than 200 characters (the longest real one is 143), or contains a control character (U+0000 to U+001F, or U+007F): a malformed identifier. N0 coordinates are counted in the ledger but written to no substrate row, so the substrate key `(pubkey, d)` is never clipped or NUL-stripped |
| N1 | any `clone` or `web` value starts with `https://nostr.life/` |
| N2 | any `clone` value contains the substring `@example.com:`, OR a tag named `euc` exists |
| N3 | `name` equals `<human-readable project name>` exactly |
| N4 | `d` matches `^20[0-9]{6}$` |
| N5 | the coordinate has at least 1,000 archived versions AND the median of the gaps (in seconds, `created_at` differences between consecutive versions in version order; the median of an even count is the mean of the two middle values) is below 300 |
| N6 | a tag whose first two elements are `deleted`, `true` exists, OR one whose first two elements are `status`, `deleted` exists, OR `name` lowercased equals `deleted`, OR a self-authored deletion exists: a kind-5 (event-deletion-requests) event whose `pubkey` equals the coordinate's pubkey, carrying an `a` tag whose value equals `30617:<pubkey>:<d>`, with `created_at` greater than or equal to the current version's `created_at` (a re-announcement after the request restarts the repository). The deletion input is the set of distinct (author, coord, created_at) triples; the horizon applies to each triple, and the newest surviving one decides |
| N7 | `pubkey` equals `79be667ef9dcbbac55a06295ce870b07029bfcdb2dce28d959f2815b16f81798` |
| N8a | there is at least one clone value, every clone value has a host (section 4.1), and every such host passes the private-host test of section 4.2 (the test itself, not the class after precedence) |
| N8b | no clone value is reachable (section 4.2 with the GRASP host set taken as EMPTY, so that a `nostr://` value on a GRASP host reads `non_network` here and the ledger never depends on 4.3, which is built from kept coordinates: there is no clone value at all, or every clone value classifies `private` or `non_network`) AND no kind-30618 (repo-states) event exists at `(pubkey, d)` |

As the last rule, it leaves an announcement of the key that an earlier rule matches in that rule's family: the 2 with no clone value are N8b. It also excludes any later announcement by the key, and a re-publication under another key is not N10) |

"No kind-30618 (repo-states) event exists" means no state row survives preprocessing at
that coordinate. The published ledger lists each family with its count in announcement
coordinates and a one-line reason; `announcements_total` = kept + the sum of the families (N0 included).

### 2.3 Repository (component)

Over KEPT announcements only. Two kept announcements A and B with the same `d` are
**joined** when A's maintainer listing contains B's pubkey AND B's maintainer listing
contains A's pubkey. A **repository** is a connected component under "joined". The
**lead** is: the unique member with `self-lead` true, if exactly one member has it;
otherwise (none, or two or more) the member with the earliest first-seen timestamp; ties
broken by the lowest pubkey (string order). The repository's `key` is `<lead pubkey>:<d>`; its `name` and
`description` are the lead's; its `first_seen` is the minimum first-seen over members; its
clone values, `web` values, `relays` values and `t` values are the union over members (order:
lead first, then the other members by pubkey); its `euc` is the lead's, else the first
member's (by pubkey) that has one. Membership is the CURRENT version's listing applied to
all history (there are no role intervals): a pubkey removed from the listing today loses its
past pushes from the repository's ledger, and one added gains them (5 coordinates today, all
`maintainer-atlas-*` test repositories).

`shared_listed_repos` uses a second, one-way relation - A and B are joined when EITHER
listing contains the other - purely to report how many components that rule would have
formed with more than one member. It does not affect anything else.

`multi_maintainer_repos` = repositories with more than one member (it and
`shared_listed_repos` are written, not shown on the page since 2026-10-02). Repository display
names fall back to `d` when the lead's `name` is empty (fork-family names too).
`maintainers` = distinct pubkeys over the members of all repositories (= distinct authors
of kept announcements). `forks` (written, not shown on the page since 2026-09-29) =
repositories whose lead announcement carries a `u` tag or a `t` value `personal-fork` (each
repository counted once; the personal-fork ones survive N9 only when they have a state).

### 2.4 Fork family

`euc` groups over repositories. `fork_families` = the number of `euc` values shared by more
than one repository. The largest families are listed with up to five repository names each
(lead names, first-seen order). Both are written, not shown on the page since 2026-09-29.

## 3. The push ledger

The ledger holds every kind-30618 (repo-states) row at a coordinate `(pubkey, d)` where
`pubkey` is a member of a repository and `d` is that repository's `d` (a **member
coordinate**), EXCEPT the state rows of a member coordinate that is a **state republish loop**: at
least 1,000 archived versions AND a median consecutive gap below 120 s (such coordinates
are counted in the ledger row `state_republish_loop`, unit: state coordinates). State
rows at coordinates that are not member coordinates are **orphan states**: ignored,
counted once in the ledger row `orphan_states` (unit: state coordinates; the state
coordinate of an excluded announcement is an orphan, so the N5 flooder's state counts
here, not as a loop). Since 2026-10-12 it also holds **hashtree pushes**, defined after the
state rules below; the column `source` tells the two apart.

Per state row, the **ref map** is the mapping from tag name to value over tags that have
at least two elements, whose name starts with `refs/heads/` or `refs/tags/` and does NOT
end with `^{}` (a one-element ref tag is ignored); when a name repeats, the first
occurrence wins. `head` is the value of the first `HEAD` tag, or none when there is no
`HEAD` tag or it has no value. The row's
flags, in version order within the coordinate:

- `changed` = there is no previous version, OR the ref map differs from the previous
  version's ref map (as a mapping: same keys and same values means equal; order and `HEAD`
  are irrelevant). The previous version is the previous version of the SAME coordinate, not
  of the repository's timeline: a member republishing the repository's current refs from its
  own coordinate is a push (5 of 2,542 multi-member pushes today).
- `head_changed` = the previous version exists and `head` differs.
- `push` = `changed` AND `created_at >= STATE_WALL`.
- Change counts (only meaningful when `changed` and a previous version exists; zero for a
  first version except `branches_added` and `tags_added`, which count the row's own refs):
  `heads_moved` (names under `refs/heads/` present in both maps with a different value),
  `default_moved` (`head` is `ref: refs/heads/X` and `refs/heads/X` moved),
  `branches_added` / `branches_removed` (`refs/heads/` names only in the new / only in the
  old map), `tags_added` / `tags_removed` (likewise for `refs/tags/`), `tags_moved`.
- `default_moved` reads the CURRENT row's `head`.

**hashtree pushes.** hashtree's git remote helper publishes a push as kind-30064
(hashtree-roots), never a kind-30618 (repo-states), and republishes the repository's kind-30617
(repo-announcements) with each ref of a public push: it loops over the push's refs and publishes
each one's root with the announcement, so a push of n refs leaves n versions, each from a few
seconds to about 107 s after the one before (observed; hashtree a60f3cd, `rust/crates/git-remote-htree/src/helper/push.rs`: the ref loop
at 1316, the publish at 1981-1993, the public-push gate at 1641-1647). So the ledger also holds a
**hashtree push** row per push at a member coordinate of a repository whose hosting class
(section 4.4) is `hashtree`. The coordinate's kind-30617 (repo-announcements) versions, in
version order (section 1 step 4), fall into groups: a version less than `HTREE_PUSH_GAP_S` =
120 s after the version before it joins that version's group, any other starts a new one. Each
group is one push, except the coordinate's first group (its creation or first push, or the
oldest versions that survived to the capture wall), and except a group whose first version's
`created_at` < `STATE_WALL`. The row is the group's first version (its `id` and `created_at`).
It has `push` and `changed` true, `head_changed` and `default_moved` false, every change count
0, and no `branches` or `tags` (the refs live inside the hashtree tree). The ledger's `source`
names the two: `htree_announcement` for these rows, `state` for every state row. They are first
written by the first run after the nostrology-data deploy of 2026-10-12 11:02 UTC; earlier documents count
no hashtree push, and carry no `pushes_hashtree_30d` (below).

Why groups, not versions: when nozzl captures a push live, every ref's version lands (two 8 s
apart and two 24 s apart on 2026-07-16); when it asks late, the relay holds only the newest
version, so one lands per push (2026-10-02 to 2026-10-12, 54 minutes to 5.6 days late, while
nozzl read this author's relays only through nos.lol). Counting versions would count refs in the
first case and pushes in the second; counting groups counts pushes in both. A gap between two
pushes under 120 s merges them, and one push whose refs come 120 s or more apart counts twice.

- Only the `hashtree` class counts this way. A `grasp_mixed` repository on GRASP and hashtree
  keeps its state rows alone, so one push sent to both is counted once. A `hashtree` repository
  that also has state rows counts both (one on row 991, with no push of either kind).
- The class is today's (section 4.4), like every hosting figure: a repository that is
  GRASP-hosted today counts none of its republishes, even from a time it was hashtree-only.
- It is mostly a lower bound, and a proxy. A private or link-visible push republishes nothing
  (the announcement would expose it), Iris Git's web app never republishes, a repository's first
  push is not counted (it is the first group; a state repository's first state is), and a push
  whose versions nozzl did not capture is missed. Two cases count too many: any other republish
  at such a coordinate, an edit of its description say, counts as a push, and a push whose next
  ref comes 120 s or more after the one before counts twice.
- kind-30064 (hashtree-roots) is not read (section 8).

Every `push` row counts: there is no per-repository or per-day cap. Before the
nostrology-data deploy of 2026-10-02 a fourth flag,
`counted`, admitted at most 50 pushes per repository per UTC day to the push figures and
reported the rest in a ledger row `daily_cap` (unit: pushes). It was dropped
because it bounded nothing that needed bounding: on 2026-10-02 it held back
375 of 19,562 pushes (1.9%), on 15 of 5,350 repository-days (0.3%), all from seven
repositories of five maintainers doing real work (the busiest, 174 pushes on 2026-09-12, a
human-plus-agent project); without it no ISO week rose more than 13.1%, the 30 d push count
rose 3.9%, and the top 20 maintainers were the same in the same order. Documents written
before that deploy - the 2026-10-02 nightly run included - carry `daily_cap`, a `counted`
substrate column and capped push figures. Reintroduce a cap only if one
repository comes to dominate the network's weekly figures.

Derived, over `push` rows of either source: `pushes_total` (written, not shown on the page
since 2026-09-29), `pushes_7d`, `pushes_30d`; `pushes_hashtree_30d` = the hashtree push rows
in 30 d (written, and the page's sign that a document counts them: first written by the first
run after the nostrology-data deploy of 2026-10-12 11:02 UTC);
`pushes_weekly` = rows `{w, pushes, repos, maintainers}` per ISO week from the week
containing `STATE_WALL` (`w` = `2026-06-08`, the value of the coverage key
`partial_first_week`) to the week containing `as_of_day` (every admitted row lies in that
range, so the series sums to the total), with `pushes` (`push` rows), `repos` (distinct
repositories with a `push` row that week) and `maintainers` (distinct pushing pubkeys that
week); weeks without rows are present with
zeros; the sum of `pushes` equals `pushes_total`. `partial_first_week` is written, not shown
on the page since 2026-10-02 (the page's weekly charts start after it). `repos_pushed_30d`,
`repos_pushed_90d` = distinct repositories with at least one `push` row in the window.
`maintainers_active_30d` = distinct `pubkey` of `push` rows in 30 d.

Per repository: `last_state` = the maximum `created_at` over its state rows (source
`state`, any flag), or none when it has no state; `last_push` = the maximum `created_at`
over its `push` rows of either source, or none; `pushes_30d` / `pushes_90d` / `pushes_total`
= its `push` rows in the window, either source; `branches`, `tags`, `head` are read from the
state row with the maximum `(created_at, -id)` over its members (the newest state). A
hashtree repository can therefore push without a state.

`repos_with_state` = repositories with a `last_state`; `no_state.total` = `repos -
repos_with_state`. Recency: over repositories with a `last_state`, `age = max(0,
as_of_day - date(last_state))` in whole days (a state dated on or after `as_of_day`, i.e.
on the run's own partial day, has age 0), bucketed `30d` (0..29), `90d` (30..89), `180d`
(90..179), `365d` (180..364), `older` (365+); the buckets sum to `repos_with_state`.
`no_state` = repositories without a state, split by hosting class (section 4.4). `recency`
and `no_state` are written, not shown on the page since 2026-10-02.
`newest_state` / `newest_push` are the UTC dates of the newest state row / newest `push`
row of either source over all repositories (none when there is none); `first_announcement` is the UTC date
of the earliest repository `first_seen`.

## 4. Hosting

### 4.1 URL parsing

For a clone or web value `u` (trimmed: Python `str.strip()` semantics, which also strip
U+001C to U+001F):

- scheme = the lowercase prefix matching `^[A-Za-z][A-Za-z0-9+.-]*://`, if any;
- scp-like when there is no scheme and `u` matches `^[^@/\s]+@[^:/\s]+:`;
- authority = for a scheme URL, the text after `://` up to the first `/`, `?` or `#`;
  host = the authority with everything up to the LAST `@` removed (userinfo) and a
  trailing `:` followed by zero or more digits removed (the port), lowercased; an empty
  host means the value has no host. For scp-like, host = the text between `@` and `:`,
  lowercased; otherwise none.
- GRASP-shaped = scheme is `http`, `https`, `ws` or `wss` AND the path (the text after the
  AUTHORITY, so a `:port` does not break the shape) matches
  `^/npub1[02-9ac-hj-np-z]{58}/`.

### 4.2 Host class

In this precedence: `hashtree` when scheme is `htree`; `private` when the host is
`localhost`, `0.0.0.0`, ends with `.local`, is a dotted IPv4 (four 1-3 digit octets,
each at most 255) in 127/8, 10/8, 172.16/12, 192.168/16 or 100.64/10, or is a `nip.io` /
`sslip.io` name whose embedded IPv4 (the four octets right before `.nip.io` / `.sslip.io`,
each separator independently `.` or `-`, each octet at most 255, and the first octet
starting the host or following a `.`, so `grasp.127.0.0.1.nip.io`, `x.10-0-0-1.sslip.io` and
`10.0-0.1.nip.io` are private while `app-10-0-0-1.nip.io` is not) is in one of those ranges; `grasp` when the host is in the GRASP host set (4.3); `forge`
when the host is one of `github.com`, `gitlab.com`, `codeberg.org`, `bitbucket.org`,
`git.sr.ht`, `tangled.org`, `gitea.com`, `gitee.com`, `framagit.org`, `notabug.org`,
`git.gittr.space`;
`non_network` when there is no host, or the scheme is not one of `http`, `https`, `ssh`,
`git`, `ws`, `wss` and the value is not scp-like; else `self_hosted`. `hashtree`,
`grasp`, `forge` and `self_hosted` are **reachable**; `private` and `non_network` are not.
Reachable is a property of the URL alone (an `htree` value, or a network URL whose host is
not private): nothing connects to the host or looks it up, so a dead host is reachable here.
The page says "public" for it.
Two consequences, recorded rather than special-cased: a `nostr://` value whose authority is
in the GRASP host set classifies `grasp` under this precedence (36 such values in 12
repositories on row 826, 2026-10-10, and no repository's class depends on them); an SSH alias host (`github.com-red`,
`github-nostrdev-com`) is a `self_hosted` host, and an scp-like value without a user
(`jb55.com:git-public/damus`) has no host (4 repositories today).
A non-network value on a forge host classifies `forge` by the same precedence
(`nostr://github.com/...`), so it counts as reachable.
`git.gittr.space` is gittr's hosted git server: it serves, over HTTPS and SSH, the
repositories of everyone who pushes to or imports through the gittr.space forge, with Nostr
keys as the accounts (185 kept repositories of 45 keys name it on 2026-10-12). It is not a
GRASP server: no Nostr relay answers at that name, and pushes are authorised by its own SSH
keys, not by a kind-30618 (repo-states) event. It is on the forge list from the first run
after the nostrology-data deploy of 2026-10-12 13:01 UTC, the
operator's decision on nostrology-data#17 (/git: 5 of the 63 hosts in the GRASP host set are not
GRASP servers and 14 are dead). Earlier documents class it `self_hosted`, and those before the
denylist of 4.3 `grasp`.

### 4.3 GRASP host set

The set of hosts `h` such that: some kept repository has a clone value that is
GRASP-shaped with host `h`; `h` contains a `.`; `h` is not private; `h` is not a forge host
(the 4.2 list: one GRASP-shaped path on github.com must not turn every GitHub-hosted
repository into a GRASP-hosted one); and `h` is on none of three hand-kept denylists:

- the web viewers and documentation sites that proxy a few repositories:
  `gitworkshop.dev`, `nostrhub.io`, `gittr.space`, `ngit.dev`;
- the general-purpose relays that serve no git: `relay.damus.io`, `nos.lol`,
  `relay.primal.net`, `relay.nostr.band`, `relay.nostrcheck.me`;
- the hosts shown not to be GRASP servers (a GRASP server is a git host that is also a Nostr
  relay, and serves each repository at its npub path):
  `git.jb55.com`, `relay.vanderwarker.family`, `gitrepublic.imwald.eu`,
  `denimroad.feeds.relay.tools`. Each was probed on 2026-10-12 with one NIP-11 (relay
  information) request and one git `info/refs` request for a repository it is named for.
  denimroad.feeds.relay.tools was
  probed again for the same repositories both ways: it serves them under `/git/<hex>/` and
  answers 404 at their npub paths. This list is first applied by the first run after the
  nostrology-data deploy of 2026-10-12 09:28 UTC; earlier documents
  count these hosts as GRASP servers. The probe found a fifth, `git.gittr.space`, which was on
  this list from that deploy until the deploy of 13:01 UTC the same day
  put it on the forge list (4.2).

A list is extended only when a host is shown to be one, and each list matches the exact host
(`relay.gittr.space`, gittr's relay, is a GRASP server). The rule is syntactic - the shape, a
dot, not private, not a forge, not listed - no DNS lookup and no connection, so a typo host,
a dead host or a `.onion` name with a GRASP-shaped path is in the set (probing each host for
GRASP support, `docs/design/ngit-design.md` fork 5, is the decided long-term
replacement for the lists; a full GRASP-01 probe of the set ran on
2026-10-13). `grasp_servers` = the size of this set. kind-10317
(grasp-server-lists) values never enter it.

### 4.4 Repository hosting class

Let R be the set of reachable host classes over a repository's clone values. In this
precedence: `grasp_only` when R = {grasp}; `grasp_mixed` when grasp is in R and R has
another member; `hashtree` when hashtree is in R (and grasp is not); `forge_only` when
R = {forge}; `other_hosts` when self_hosted is in R (no grasp, no hashtree); `none` when R
is empty. The six classes partition the kept repositories. Each condition excludes the other
five even without the precedence, and every R, any of the 16 subsets of the four reachable
host classes, meets exactly one (`test_repo_hosting_classes_partition_every_reachable_set`
in nostrology-data enumerates them; on 2026-10-10, row 826, every one of 4,596 repositories
met exactly one, and 11 of the 16 sets occur). So `hosting` sums to `repos`, which the
pipeline asserts. A fifth reachable host class needs a class of its own here first: the
precedence alone would put a repository on it alone, or on it and forges only, in `none`.
`grasp_repos` = `grasp_only` + `grasp_mixed`; `grasp_share` = `grasp_repos /
repos` (0 when `repos` is 0; shares are unrounded); `grasp_share` is written, not shown on the
page since 2026-10-10. The page's headline share, on its card and in the hosting donut's
centre, is GRASP or hashtree: (`grasp_repos` + the `hashtree` class) / `repos`, 0 when
`repos` is 0, computed on the page from the document's counts. It is the repositories with a
clone URL on a GRASP server or an `htree://` clone URL: a repository on both is `grasp_mixed`
(5 on row 826), so the exclusive classes count each once. Repositories on single-use keys with test-like names are kept in
every class (`docs/design/ngit-design.md` section 5), and they weigh on `hashtree`

A repository's `grasp` flag (the substrate column) is true exactly when its class is
`grasp_only` or `grasp_mixed`. Every row
of the document's repository lists carries its repository's class as `cls`: `repos_active`,

### 6.2 Stars

Stars come in two kinds, depending on the client that sent them. Each yields a set of
`(pubkey, target coordinate)` stars.

**kind-7 (reactions)**, as gitworkshop.dev and gittr send them. The input is every kind-7
(reactions) row with a `k` tag valued `30617` or an `a` tag whose value starts with
`30617:`. A star is such a row whose `content` is `+` or `""`. Its target
coordinate is the first `a` value starting `30617:` parsed as above; when there is no `a` value starting `30617:` at all (a malformed one
does not fall back to `e`), the first `e` tag's value looked up among the ids of all archived kind-30617
(repo-announcements) versions that survive preprocessing (section 1), yielding that
version's coordinate; a star with no
resolvable target is dropped. Unstars are not observed: gitworkshop.dev unstars with a
kind-5 (event-deletion-requests) of the reaction, which this surface does not read for
reactions.

**kind-17 (external-content-reactions)**, as Iris Git (hashtree's web app) sends them: a
reaction to the repository's coordinate, written as external content. The input is every
kind-17 (external-content-reactions) row with a `k` tag valued `git-repo` AND an `i` tag
whose value starts with `30617:`. Its target coordinate is the first `i` value starting
`30617:`, parsed as `30617:<pubkey>:<d>` as above (`d` is everything after the second
colon). A value without a second colon names no coordinate: the row is dropped from the
stars, with no fall-through to a later `i` value, but it stays in the input, so
`summary.archive_events` and the anomaly slots count it. The remaining rows are grouped by
(the row's `pubkey`, target coordinate). Within a group the version order of section 1
step 4 applies (`created_at` ascending, then `id` descending), and the last row is that
key's current reaction to that coordinate. It is a star when its `content`, trimmed (Python
`str.strip()` semantics, as section 4.1 pins for clone values), is `+` or `""`; anything
else is not, Iris Git's unstar `-` included. Stars on the Iris Git test runs the roster
keeps (section 4.4) count like any others.

This is Iris Git's own count - each reactor's latest reaction counts when its trimmed content
is `''` or `+`, the owner's own included - with four deliberate differences, none of which
changes a star on the archive of 2026-10-11:
- **The tie.** Iris breaks a same-second tie by processing order (the later event wins);
  this rule takes the lowest id, as NIP-01 (protocol basics) does.
- **The target.** Iris takes the first `i` value that splits into exactly three parts,
  skipping a malformed one, so it never counts a `d` that contains `:`. This rule takes the
  first `30617:` value with no fall-through, and keeps colons in `d`, as the comment and
  kind-7 (reactions) rules do; three kept coordinates had a `:` in `d` on 2026-10-11.
- **The trim.** Python's `str.strip()` also removes U+001C to U+001F and U+0085, which
  JavaScript's `trim()` keeps, and keeps U+FEFF, which `trim()` removes.
- **The repository.** Iris counts per announcement coordinate; this rule maps each
  coordinate to its repository (section 2), so a key that stars two member coordinates of
  one repository makes one pair.

A kind-5 (event-deletion-requests) naming a
kind-17 (external-content-reactions) is not read, as Iris Git does not read one. A kind-17
(external-content-reactions) unstar withdraws only that key's star of that kind: a kind-7
(reactions) star by the same key on the same repository stays.

A star of either kind counts when its target is a member coordinate of a repository.
`stars_total` = distinct `(pubkey, repository key)` pairs over both kinds, so a key that
starred one repository from both clients counts once (written, not shown on the page since
2026-10-18); `stars_iris` = the distinct pairs
from kind-17 (external-content-reactions) stars alone, whether or not the same pair also has
a kind-7 (reactions) star (written, not shown on the page); `stars_repos` = repositories
with at least one (not shown on the page since 2026-10-18 either, but read: it decides whether
the stars table says that sorting reorders the rows shown only); `repos_starred` = top 20 by
stars, then key; the top 10 before the first run after the nostrology-data deploy of 2026-10-18
06:14Z. Each repository's
count is in `ngit_repo_stats` (section 9). `stars_iris` is first
written by the first run after the nostrology-data deploy of 2026-10-11; documents generated
before 2026-10-12 may lack it, and such a document counts kind-7 (reactions) stars alone.
Every document generated from 2026-10-12 on carries it: one without it is a regression. A star is one per key with no
proof behind it: fifty fresh keys make fifty stars, so `stars_total` is a lower bound on
attention and no bound at all on Sybils.

### 6.3 Zaps

The input is every kind-9735 (zap-receipts) row with an `a` tag whose value starts with
`30617:`. Its coordinate is the first such `a` value. The receipt's amount in
millisatoshis is read from its LAST `bolt11` tag that has a value (the shared
`zap_parser`'s bolt11 amount parser); a `bolt11` value longer than 2,048 characters, or
one whose parsing raises any error, is "no readable amount". A receipt with no readable
amount, or with an amount above 21,000,000,000 msats (0.21 BTC, the /lightning spam filter), is
dropped; the counted amount is the minimum of the amount and 10,000,000,000 msats (0.1 BTC,
the /lightning cap). The zapper is the
pubkey of the embedded zap request (kind-9734 (NIP-57 zap request), the `description`
tag: the LAST `description` tag that has a value, parsed as a JSON object with a
non-empty string `pubkey`) when it parses; a description longer than 65,536 characters,
or one whose parsing raises any error (including a recursion error on deep nesting), does
not parse; a receipt whose description does not parse still counts, with no zapper. A
readable amount of 0 msats is kept. The `bolt11` and `description` tags
'have a value' when they have a second element, even an empty string (an empty bolt11 is
then 'no readable amount'). A receipt counts when ALL of these hold: its coordinate is a
member coordinate of a repository; its `pubkey` (the receipt's signer) is one of the
verified LNURL provider signer keys - every key in the `signers` list of every provider in
`data/lightning/provider_signers.yaml` (each verified against the provider's
NIP-57 (lightning zaps) `nostrPubkey`; the list /lightning uses) - so a
receipt anyone can fabricate under an unlisted key never counts, and a receipt from a real
provider not yet on the list is missed until it is added (25 of the 26 receipts of
2026-09-25 pass; the one lost is 21 sats); its first `p` tag value, compared exactly as published (no
case folding), is a member pubkey of that repository (the zap paid a maintainer); and, when
the embedded request parses (the zapper parse below: a JSON object with a non-empty string
`pubkey`) and its FIRST `amount` tag has a non-empty value, that value equals the bolt11
amount in millisatoshis as decimal text (NIP-57 (lightning zaps) appendix F; `0500000` is a
mismatch, and so is a JSON number in place of the string; a JSON `null` is no value; a request
without an `amount` tag, or one that does not parse, does not block the receipt). The counted receipts give
`zap_receipts`, `zap_msats` (sum of counted amounts; written, not shown on the page since
2026-10-18), `zappers` (distinct zapper pubkeys), `zaps_repos`; `repos_zapped` = top 20 by
receipts, then msats, then key. It ranked by msats, then receipts, then key before the first
run after the nostrology-data deploy of 2026-10-18 07:34Z, and held the top 10
before the first run after its deploy of 06:14Z that day; each was the operator's
ask. Each repository's figures are in `ngit_repo_stats` (section 9).

  those whose hosting class TODAY is `grasp_only` or `grasp_mixed`, `other` = the rest,
  `v` = `grasp` + `other`; `s` = maintainers whose earliest kept announcement's first-seen
  month is that month. Months before `ANN_WALL` hold survivors only. Written, not shown on
  the page since 2026-10-02.
- `new_repos_weekly`: the same rows `{w, v, grasp, other, s}` per ISO week of `first_seen`
  (`s`: the week of the maintainer's earliest kept announcement's first-seen), zero-filled
  from the week containing `ANN_WALL` (`2026-04-27`) to the week of `as_of_day`; a repository
  or maintainer first seen before that week is in no week. Each row also has `by_host` =
  `[{k, v}]`, the week's repositories by the kinds of public host they are on TODAY: one
  entry per reachable host class of section 4.2 in the section 4.4 precedence order, then
  `none` - `grasp`, `hashtree`, `forge`, `self_hosted`, `none` - every entry present with
  zeros included. For a host class `k`, `v` = the week's repositories whose R (section 4.4)
  contains `k`; for `none`, those whose R is empty (hosting class `none`). A repository
  counts once in every kind in its R - a GRASP server and a GitHub mirror count under both
  `grasp` and `forge` - so the entries can sum to more than the row's `v`, never to less;
  `grasp`'s `v` = the row's `grasp`. `by_host` is first written by the first run after the
  nostrology-data deploy of 2026-10-08 (UTC); documents generated before 2026-10-09 may
  lack it. Since 2026-10-08 the page draws `by_host`, and the rows' `grasp` and `other` are
  written, not shown.
- The three weekly series (`new_repos_weekly`, `comments_weekly`, `grasp_lists.per_week`)
  each start with the week holding their kind's capture wall. Every row dated in that first
  week counts in it, on either side of the wall instant, so the week mixes what relays still
  served from before the wall with what was captured after it; no coverage key flags it (the
  page starts its weekly charts with the week of 2026-06-29, the week holding 2026-07-01,
  after every wall). They are first written by
  the first run after the nostrology-data deploy of 2026-10-02, and earlier documents lack
  them.
- `cum_repos`: per UTC day from the earliest `first_seen` to `as_of_day`, the number of
  repositories with `first_seen` on or before that day; consecutive equal days may be
  elided, but the first day, every day the count changes and `as_of_day` are present.
- `partial_month` = the month of `as_of_day` when `as_of_day` is not its last day, else
  none (written, not shown on the page since 2026-10-02: the page draws no monthly series);
  `partial_week` = the ISO week of `as_of_day` when `as_of_day` is not a Sunday, else none.

## 8. What these numbers are NOT

- Not an exhaustive count of repositories on Nostr: only of the ones our relays served, after
  the ledger. Until 2026-10-09 that was four relays: nos.lol, damus, primal and
  relay.ngit.dev. Since then it is nine, adding relay.ditto.pub and the GRASP servers
  gitnostr.com, git.shakespeare.diy, ngit.danconwaydev.com and grasp.budabit.club, and since
  2026-10-12 ten, adding index.ngit.dev (section 0, item 1). A repository whose events never reached one of them is invisible. The page states
  this without naming relays.
- Not commits: a push is one state publication that moved at least one ref, or one hashtree
  push read from its republished announcements (section 3), however many commits it carried.
- Not every hashtree push: hashtree's git remote helper publishes a push as a kind-30064
  (hashtree-roots), never a kind-30618 (repo-states). Since the nostrology-data deploy of
  2026-10-12 11:02 UTC a `hashtree` repository's push is counted from the announcement its git tool
  republishes with each ref of a public push (section 3); until then no hashtree push was
  counted, and the page said so from 2026-10-09 (`docs/design/ngit-design.md` section
  13.1). A private or link-visible push republishes nothing, Iris Git's web app never does, a
  repository's first push is not counted, and a push nozzl did not capture is missed. /git
  does not read kind-30064 (hashtree-roots): one push's roots, one per changed ref, arrive
  30-107 s apart.
- Not verified projects: a kept repository is an announcement that survived the ledger.
- Not issue or PR counts: nothing here reads the issue, patch and pull request events;
  discussion is counted by root kind network-wide and attributed to a repository only when
  the comment names one.
- Not net of every unstar: a kind-7 (reactions) star is withdrawn by a deletion request, and
  those are not read for reactions; a kind-17 (external-content-reactions) star is withdrawn
  by its key's later `-`, which is read (6.2).
- Not verified payments: a counted zap receipt is signed by a listed LNURL provider key
  (6.3), which is what makes it plausible, not proof that the invoice was paid; nothing
  checks the receipt against the provider or the invoice.
- Not Sybil-resistant: a star is one per key (6.2).
- Not case-folded: coordinates whose `d` differs only by letter case or outer whitespace
  are distinct repositories, as NIP-01 (protocol basics) compares `d` exactly (17 such
  groups today, about 0.4%).
- Not activity before 2026-06-14: the surviving version's date is a lower bound on the
  last change, not a push.

## 9. Cross-check contract and the substrate columns

`crosscheck/ngit_check.py` re-derives, from the raw archive pinned at `--ingested-before <the
Dagster run's start>` with `--now <generated_utc>` (the extracts read the archive minutes
before the compute step stamps `generated_utc`; a pin at `generated_utc` can only add false
differences from events ingested during the run, never hide one), the substrate rows below, the `summary` block minus names
and, since 2026-10-02, the four weekly series (`pushes_weekly`, `new_repos_weekly` and
`comments_weekly` at the document's top level, `per_week` inside `grasp_lists`; since
2026-10-08 `new_repos_weekly` with its `by_host`, entry by entry and as its sequence of
keys), compared row by row and as a sequence of weeks, and diffs
them against the `ngit_repos` / `ngit_pushes` export and the newest `ngit_snapshot` row;
the contract is zero differences. A difference is either a bug in one implementation or an
ambiguity in this document - and an ambiguity is fixed HERE first.

The checker implements the rules as they stand now. Three changes of 2026-10-12 apply from the
deploy that brought each: the third denylist of section 4.3 and `git.gittr.space` on the forge
list of section 4.2, which no document marks, and the hashtree pushes of section 3, which a
document marks by carrying `pushes_hashtree_30d` (the checker does not choose its rule by it). A
row written before such a deploy re-derives with differences wherever the change decides a
figure, so check it with the checker as it was before that change (its header gives, by date, the
version each older row needs). A fourth, N10 (section 2.2), changes no older row: no announcement by its
key was archived before the deploy that brought it, and the `N10` row an older document lacks
reads as 0 (N10 came with the nostrology-data deploy of 18:27 UTC).

### 9.1 The recipe (verified against the live schema 2026-09-25)

Everything runs from a workstation; the box side is psql over a read-only login on the box
(`$NOSTROLOGY_RO_SSH` is its ssh destination, and `$NOSTROLOGY_DAGSTER_GRAPHQL` the read-only
Dagster UI's GraphQL URL as the box sees it) and nothing is written on the box, so there is
nothing to clean up. `<dir>` is a scratch directory.

```sh
# 0. The served row: its run id and generated_utc (the --now pin). Rows are append-only and
#    the substrate tables are reloaded by every run, so re-run this line AFTER step 2 and
#    require the same run_id, or the export and the row are from different runs.
ssh "${NOSTROLOGY_RO_SSH:?}" 'H=$(cut -d: -f1 ~/.pgpass | head -1); PGCONNECT_TIMEOUT=30 psql -h "$H" -U nostrology_ro -d nostrology -XAt \
  -c "select run_id, generated_utc from ngit_snapshot order by generated_utc desc, id desc limit 1"'

# 1. The run START (the --ingested-before pin), from Dagster BY THAT RUN ID - not from
#    last-run-ngit_refresh.json, which names the newest run even when that run failed.
#    startTime is epoch seconds with a fraction: drop the fraction, then
#    date -u -r <startTime> +%FT%TZ on macOS (-d @<startTime> on GNU).
ssh "${NOSTROLOGY_RO_SSH:?}" 'curl -s -X POST '"${NOSTROLOGY_DAGSTER_GRAPHQL:?}"' -H "content-type: application/json" \
  -d "{\"query\":\"{ runOrError(runId:\\\"<run_id>\\\") { ... on Run { startTime } } }\"}"'

# 2. The export, streamed straight to the workstation. CSV with a header; booleans arrive as t/f,
#    which the checker accepts. The document is read with a plain SELECT, never \copy in
#    text format, which would double every backslash in third-party names.
ssh "${NOSTROLOGY_RO_SSH:?}" 'H=$(cut -d: -f1 ~/.pgpass | head -1); PGCONNECT_TIMEOUT=30 psql -h "$H" -U nostrology_ro -d nostrology -XAt \
  -c "\copy (select * from ngit_repos order by pubkey, d) to stdout with (format csv, header)"' > <dir>/ngit_repos.csv
ssh "${NOSTROLOGY_RO_SSH:?}" 'H=$(cut -d: -f1 ~/.pgpass | head -1); PGCONNECT_TIMEOUT=30 psql -h "$H" -U nostrology_ro -d nostrology -XAt \
  -c "\copy (select * from ngit_pushes order by repo_key, created_at, event_id) to stdout with (format csv, header)"' > <dir>/ngit_pushes.csv
ssh "${NOSTROLOGY_RO_SSH:?}" 'H=$(cut -d: -f1 ~/.pgpass | head -1); PGCONNECT_TIMEOUT=30 psql -h "$H" -U nostrology_ro -d nostrology -XAt \
  -c "select data from ngit_snapshot where run_id = '"'"'<run_id>'"'"'"' > <dir>/summary.json

# 3. The check: about ten minutes (the roster kinds are scanned from S3 one partition at a
#    time; the three heavy kinds come from the run's own Athena UNLOAD parts), with
#    AWS_PROFILE, NOZZL_ARCHIVE_BUCKET and NOSTROLOGY_EXTRACTS_BUCKET set, as the pipeline reads them.
.venv-crosscheck/bin/python crosscheck/ngit_check.py --s3 \
  --now <generated_utc> --ingested-before <run start> --heavy-from-extracts <run_id> \
  --out <check dir> --compare <dir>
```

Three things the recipe depends on:

- **The heavy-kind inputs expire.** The run's UNLOAD parts are deleted by an S3 lifecycle
  rule 7 days after the run; past that, `--heavy-from-extracts` cannot load the reactions,
  zap receipts and deletion requests and the check stops with exit 2, naming the kind, the
  run id and the prefix (it must not fall back to empty inputs, which would blame N6 and
  every social figure on the pipeline; `--allow-empty-heavy` does exactly that, on purpose,
  with a warning). Re-run the pipeline and check the new row, or scan those kinds from S3
  without the flag. Exit 2 means "could not run"; `--compare`'s exit 1 means differences.
- **The pin is the run start, and it is a few seconds coarse.** Each of the eight extracts
  flushes its kind's WAL at its own moment, seconds to a couple of minutes after the run
  start, and reads the archive as of that flush; `--ingested-before` is one instant for
  all kinds and is inclusive (rows with `ingested_at` equal to the cutoff are kept). A
  difference confined to rows ingested between the run start and that kind's
  `[extract] flushing` log line is therefore the pin's imprecision, not a bug; a pin
  later than the run start (for example at `generated_utc`) can only add such
  differences, never hide one. A hashtree push (section 3) is a group of versions, so a
  difference in an `htree_announcement` row can come from ANY version of its coordinate
  ingested in that window, not only from the row's own event: a late version can join or
  split a group whose first version was ingested long before.
- **The comparison ignores presentation.** `name`, `hosts` and `relays` are not compared,
  nor are the names and the `concentration` block of the document (see below).

`ngit_repos` - one row per announcement coordinate (all of them except N0, which have no
row):

| column | level | meaning |
|---|---|---|
| `pubkey`, `d` | coordinate | the coordinate (`d` as published; N0 keeps any `d` over 200 characters out - the longest real one is 143) |
| `family` | coordinate | `repo`, or the ledger rule that matched (`N1` .. `N10`, `N8a`, `N8b`) |
| `repo_key` | repository | `<lead pubkey>:<d>` for kept rows, NULL otherwise |
| `is_lead` | coordinate | this coordinate is its repository's lead |
| `name` | coordinate | current version's `name`, control and format characters (Unicode categories Cc and Cf) removed, clipped to 80 |
| `first_seen`, `last_seen`, `versions` | coordinate | earliest / current version `created_at`; archived version count |
| `cls`, `grasp` | repository | hosting class; `grasp` = the class is `grasp_only` or `grasp_mixed` (kept rows; section 4.4) |
| `hosts` | coordinate | JSON list of `{host, cls}` over this coordinate's clone values, distinct, at most 20 |
| `relays` | coordinate | JSON list of normalized relays, at most 20 |
| `euc` | coordinate | the coordinate's euc, or NULL |
| `tool` | coordinate | the tools heuristic applied to this coordinate |
| `has_state` | coordinate | a state row exists at `(pubkey, d)` |
| `last_state`, `last_push` | repository | as in section 3 (kept rows; NULL when none) |
| `pushes_total`, `pushes_30d`, `pushes_90d` | repository | pushes (kept rows; 0 otherwise) |

`ngit_pushes` - one row per state version of a kept repository's member coordinates,
excluding state republish loops, and, since the nostrology-data deploy of 2026-10-12 11:02 UTC, one row
per hashtree push (section 3):

| column | meaning |
|---|---|
| `event_id`, `pubkey`, `d`, `repo_key`, `created_at` | the state version, or the hashtree push's kind-30617 (repo-announcements) version, and its repository |
| `changed`, `push`, `head_changed` | the flags of section 3 (the `counted` column was dropped by the nostrology-data deploy of 2026-10-02) |
| `heads_moved`, `default_moved`, `branches_added`, `branches_removed`, `tags_added`, `tags_removed`, `tags_moved` | the change counts of section 3 |
| `branches`, `tags` | this version's `refs/heads/` and `refs/tags/` counts (no `^{}`); NULL on a hashtree push |
| `source` | `state` or `htree_announcement` (a hashtree push); added by the nostrology-data deploy of 2026-10-12 11:02 UTC, and an export from before it has no such column |

The check compares every column except `name`, `hosts` and `relays` (presentation
lists), and compares the `summary` block field by field except `concentration` (derived)
and the names. The `coverage` block (the capture dates and the `partial_*` keys) and the
document's other lists are outside the comparison. `name` has control and format characters (Cc, Cf) removed and is clipped to 80; `d` is stored as is (N0 keeps
malformed identifiers out); `repo_key` carries the same `d`. The ledger (`exclusions`) has exactly these keys,
every one present even when zero: `N0` .. `N7`, `N8a`, `N8b`, `N9`, `N10` (unit
`announcements`), `state_republish_loop`, `orphan_states` (unit `state coordinates`),
`ephemeral`, `imported`, `mirrored` (unit `comments`). Documents written before the
nostrology-data deploy of 2026-10-02 also carry `daily_cap` (unit `pushes`; section 3), and
documents written before the nostrology-data deploy that brought N10 (2026-10-12 18:27 UTC)
lack `N10`.

### 9.2 The per-repository figures (`ngit_repo_stats`)

One row per kept repository (section 2.3), written since the
nostrology-data deploy of 2026-10-18 11:26Z. The page
lists Stars and Zaps from it since the nostrology-web deploy of 11:37Z that day,
and the document's `repos_starred` and `repos_zapped` are its top 20 under
sections 6.2 and 6.3, which the pipeline holds before any write:

| column | meaning |
|---|---|
| `repo_key` | `<lead pubkey>:<d>`, as in `ngit_repos` |
| `run_id` | the run whose `ngit_snapshot` row was written with it, in the same transaction: a reader pairs the two by it |
| `pubkey`, `d` | the lead coordinate |
| `name` | the lead's `name`, else its `d`, control and format characters (Cc, Cf) removed, clipped to 80: the document's rows carry the same |
| `cls` | the repository's hosting class (section 4.4) |
| `stars` | its distinct `(pubkey, repository)` star pairs (section 6.2); 0 when none |
| `zap_receipts`, `zap_msats` | its counted receipts and their counted amounts in millisatoshis (section 6.3); 0 when none |

Over the table, `stars` sums to `stars_total`, and `zap_receipts` and `zap_msats` to the
summary's figures of the same names; the repositories with a star are `stars_repos`, those

code-point order (the page's query sorts with `COLLATE "C"`, which is the same). The checker
does not yet re-derive this table; its figures are held to the summary, which it does.
